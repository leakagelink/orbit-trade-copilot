# Phase 4H.1 security review — Futures paper worker identity (13 Nov 2026)

**Scope.** This review covers drafts 0049–0054 (none applied) and the disabled worker code:
- `src/lib/futures-paper-worker*.ts`;
- `futures-paper-worker-identity*.ts`.

**What was and was not done.**
- No account, secret, deployment or credential was created.
- No hosted write was made.
- One read-only hosted catalog query was run: no draft is applied; `has_role` is SECURITY DEFINER with `search_path=public`; roles are `user`, `admin`, `super_admin`; `account_mfa_allowed()` exists; the server is PostgreSQL 17.11.

## Verdict by layer

| Layer | What it gives | Status |
|---|---|---|
| **A. Database-level authorization** | Checks inside SECURITY DEFINER functions with a fixed `search_path`. These checks cannot be skipped by any client code. Each of the six `fpw_id_*` worker functions re-checks, on every call, that the signed-in caller is now:<br>• an enabled identity;<br>• not an admin or super_admin;<br>• not the owner of any paper account;<br>• enrolled (not revoked) by the account's current owner.<br>The four writing functions hold FOR SHARE locks on those rows. The 0050 gateway is not executable by `service_role`, `anon`, `authenticated` or PUBLIC | **Implemented in drafts 0053 and 0054; tested locally** on PGlite and real PostgreSQL 17.11. **Not verified on the hosted database** (not applied) |
| **B. Application-level code allowlisting** | The worker code can name only six functions (`HOSTED_WORKER_RPCS`) and maps them to the six wrappers (`identityRpcName`); any other name throws. Nothing imports the identity binding. Both activation flags are unset | **In place, but it is not a security boundary.** Any other code running in the same server runtime is not bound by this list |
| **C. Runtime-level credential isolation** | This would require a runtime that holds only the worker's credential and **not** the service-role key | **NOT ACHIEVED. BLOCKED.** The worker would run in the app's server runtime, which holds `SUPABASE_SERVICE_ROLE_KEY`. 43 non-test source files mention the privileged server-client module (`client.server`). A compromise of that runtime, or any code path in it, gets full service-role power whatever the worker signs in as |

A signed-in worker identity narrows what **the worker's own credential** can do (layer A). It does **not** give runtime isolation (layer C). This review does not claim otherwise.

## Findings

| # | Area | Finding | Status |
|---|---|---|---|
| F1 | Identity lifecycle (0053) | `fpw_admin_set_identity` applied the "separate plain user" rule even when **disabling**. A worker promoted to admin or super_admin, or one that came to own a paper account, could therefore never be disabled | **Fixed in 0054.** Disabling needs only a signed-in admin with MFA and an existing identity. Re-enabling re-checks eligibility. Tests 5, 5b, 6, 7; mutation M1 caught |
| F2 | Authorization (0053) | `fpw_id_authorize` checked only `enabled` and the enrollment. A worker promoted to admin or super_admin, or one that became an account owner, kept working | **Fixed in 0054.** `fpw_id_check` re-checks the current status on every call. Tests 2, 3, 4; mutations M2–M4 and M10 caught |
| F3 | Revocation timing (0053) | A disable or revoke could commit while a worker write was in flight, and that write would still commit afterwards | **Fixed in 0054.** Writing wrappers take FOR SHARE on the identity and enrollment rows. A disable or revoke waits for the in-flight write; a worker call waiting on a committed disable re-reads the row and is refused. Real-PostgreSQL tests 1–3; lock-removal mutation caught (3 failing) |
| F4 | Residual race | A role promotion (insert into `user_roles`) or the creation of a paper account for the worker, committed while one worker call is running, can let that single call finish. The next call is refused. `user_roles` is not locked (owned by the app's role system) | **Documented residual** |
| F5 | Owner enrollment (0053) | An owner could enroll an identity that had since become ineligible | **Fixed in 0054** (same eligibility rule). Test 2; mutation M11 caught |
| F6 | Identity change history (0053) | Registry changes kept only `updated_by` / `updated_at`; earlier states were lost | **Fixed in 0054.** Append-only `futures_paper_worker_identity_changes`: no update, delete or truncate even for the table owner, and no API-role access. Racing changes are recorded in order (12-session real-PostgreSQL test) |
| F7 | `search_path` | Every SECURITY DEFINER paper function has a fixed `search_path` (checked in the catalog). 0049–0053 use `'public'` with schema-qualified table names. 0054's functions use `'public', 'pg_temp'` (pg_temp last) | **Verified** (PGlite test, local verifier) |
| F8 | Grants | After 0054:<br>• PUBLIC, `anon` and `service_role` have EXECUTE on no identity function;<br>• `authenticated` has EXECUTE only on the admin, owner and six wrapper functions;<br>• `fpw_id_check` and `fpw_id_authorize` are executable by no API role;<br>• the six 0050 gateway functions stay revoked from `service_role`;<br>• 0054 adds no grant to PUBLIC, `anon` or `service_role`.<br>A refused 0053 rollback (run in one transaction) restores no service-role access | **Verified** (PGlite test, change-control test, local verifier, mutation M12 caught) |
| F9 | Sign-in and token refresh (`futures-paper-worker-identity.server.ts`, disabled) | • Each binding signs in with email and password using the publishable key, with `persistSession: false` and `autoRefreshToken: true`.<br>• In auth-js 2.118.0 outside a browser, no background refresh timer starts. The ticker starts only from `startAutoRefresh()` or browser visibility events (checked in the library source). Instead, the access token is refreshed on demand when it is within 90 s of expiry (`EXPIRY_MARGIN_MS` = 3 × 30 s).<br>• Sessions are never signed out, so each sign-in leaves a session and refresh token on the auth service until they expire.<br>• Repeated password sign-ins may meet the auth service's sign-in rate limits.<br>• Access-token lifetime and rate limits on the hosted auth service were **not verified** | **Open, not fixed.** The code was not changed this phase. Recommendation for the activation design: one sign-in per tick, local sign-out at the end of the tick, a tick deadline well under the token lifetime, and an explicit bounded failure code for auth errors (`IDENTITY_SIGN_IN_FAILED` exists; an expired token mid-tick returns PostgREST code PGRST301, which `classifyRpc` treats as transient, so nothing is written) |
| F10 | Secrets and environment | • The identity binding reads four variables (`SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `FUTURES_PAPER_WORKER_EMAIL`, `FUTURES_PAPER_WORKER_PASSWORD`) and two flags. It reads them inside the function, never at import.<br>• Provider error text is never forwarded (bounded codes only).<br>• Nothing logs values.<br>• None of these variables is set in the project.<br>• Lovable Cloud secrets are project-scoped. The docs describe no per-function secret scope, so a worker password stored as a project secret would be readable by all server code — exactly like the service key | **Documented.** Activation needs owner decisions |
| F11 | Import graph | • Nothing in the app imports either identity file or the hosted binding (`futures-paper-worker-hosted.server.ts`).<br>• No route, schedule or cron entry names the worker.<br>• The hosted binding imports the privileged client but is disabled by an unset flag | **Verified** by isolation tests |
| F12 | Lease and fencing (0050, unchanged) | • The lease is per account (TTL 10–300 s) with a monotonically increasing fence.<br>• Commit and mark-review check holder, fence and `expires_at > clock_timestamp()` inside the database.<br>• A lost lease is transient; a timeout means the identical payload is resent once.<br>• 0054 adds identity/enrollment locks only to the writing wrappers and leaves lease semantics alone | **Unchanged.** Covered by the existing real-PostgreSQL suites (43/43 ×3) |
| F13 | Audit integrity | • The worker audit (0050), config changes (0052, hash-chained) and identity changes (0054) refuse update, delete and truncate through triggers.<br>• Limits:<br>&nbsp;&nbsp;– a database superuser or table owner can disable triggers (owner-level trust);<br>&nbsp;&nbsp;– refused worker calls leave no audit row, because they roll back with the call;<br>&nbsp;&nbsp;– monitoring must come from the worker's bounded metric codes | **Documented** |
| F14 | Error handling and retry | • A refused lease acquire leaves the account unprocessed.<br>• A refused snapshot or commit (P0001, including the new "no longer eligible" message) goes to the refusal planner. An unknown message leads to an attempted review hold, which is itself refused for an ineligible worker (`REVIEW_HOLD_NOT_RECORDED`). **Nothing is written**, which fails closed.<br>• No blind retries: only one identical resend after a lost reply.<br>• Verified: a disabled worker's tick commits 0 candles (test 9) | **Verified** |
| F15 | Signed-in user rights | An enrolled worker identity is also an ordinary signed-in user elsewhere in the app. Row-level security returns only rows it owns (none). It should own no other data | **Documented residual** |

## Can the worker run without the service-role key? (feasibility investigation, no action taken)

| Option | Feasibility | Notes |
|---|---|---|
| Same app runtime (current design) | Works | **Not isolated** (layer C fails). The service key is present |
| Separate Lovable project holding only the publishable key and worker credentials, calling this backend through the public Data API | **Plausible, not verified** | Lovable docs say secrets are project-scoped and describe no separate-worker deployment inside one project. A second project would have its own secret set, without this backend's service key. Not verified:<br>• that a project without its own Cloud backend can store secrets and run scheduled server code;<br>• how it would be triggered (a schedule in this backend calling a public route of the other project would need its own caller verification);<br>• costs.<br>Needs owner approval; nothing was created |
| Backend edge functions | Not used | The platform's rules for this stack direct server logic to the app's server functions, not edge functions |
| External infrastructure (e.g. the owner's own Workers account) | Technically possible | Needs owner approval and may be paid. Out of scope; not investigated further |
| Worker inside the database (scheduled SQL) | Not feasible as designed | The engine and market-data fetch are TypeScript, and the database would need outbound HTTP |

**Conclusion.** Runtime isolation is **BLOCKED** pending an owner decision on a separate deployment. Until then, worker security rests on layer A alone, inside a runtime that also holds full service-role power.
